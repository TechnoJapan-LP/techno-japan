# ビジュアル参考: EYESCREAM / Spincoaster 実測レポート（2026-09-29）

同じ計測スクリプト（headless Chrome・PC 1440×900 / モバイル 393×852 dpr3、最下部までスクロールして遅延読み込みを発火）で
3サイトを測り、見せ方の違いを数字で比べた。スクリーンショットと生データは scratchpad（`probe_*.json`）。

## 0. 数値サマリー

| 指標（モバイル 393px 実測） | Techno Japan TOP | Techno Japan フェス一覧 | EYESCREAM | Spincoaster |
|---|---|---|---|---|
| ページ内の画像枚数 | **3** | **2** | 14 | **46** |
| 1画面あたりの画像数 | 0.4 | **0.3** | 0.7 | **4.7** |
| 画像の転送量（最下部までスクロール） | **1,082KB** | **13KB** | **33,043KB** | **13,732KB** |
| 画像 1 枚あたり | **57KB** | 6KB | 542KB | 292KB |
| ページ全体 | **1,261KB** | 196KB | 33,883KB | 15,155KB |
| srcset / 実寸選択 | 全カード（2026-09-29 導入） | 同左 | 10 / 14 | 44 / 46 |
| 文字サイズの最頻値 | **8〜10px** | **8〜10px** | 12・16px | **14〜16px** |

> ⚠ **2026-09-29 訂正。** 初版は Spincoaster を「46枚 / 539KB」と書いていたが**誤り**。
> 同社の画像は別ドメイン（storage.spincoaster.com）配信で、`performance.getEntriesByType('resource')` は
> 他ドメインの `transferSize` を 0 で返す（Timing-Allow-Origin が無いため）。自サイトの画像しか数えていなかった。
> 上表は Chrome DevTools Protocol の `Network.loadingFinished.encodedDataLength` で測り直した値。
> Techno Japan 側は Service Worker のキャッシュを迂回（`Network.setBypassServiceWorker`）して計測している。
> **AGENTS.md「実測したと言う前に、測っているものを確かめる」に該当する誤りだった。**

**Techno Japan は 420枚の写真を持っている**（フェス143 / 記事225 / アーティスト30 / 会場22）のに、
**フェス一覧で出しているのは2枚**。一方で**転送量は3サイトで圧倒的に軽い**（競合の 1/12〜1/27）。

つまり構図はこうである:

- **Techno Japan は軽さで勝っていて、密度で負けている。** Spincoaster の 4.7枚/画面は 13.7MB を払って実現している。
- したがって「容量の制約で写真を出せない」わけではない。**1.3MB → 2MB 程度まで使っても、なお競合の 1/7 に収まる。**
- 同時に、内部には実測で分かった無駄があった — 64px の枠に 960px の画像を送っていた（artists.html のカード137枚）。
  これは 2026-09-29 に修正済み（artists.html 1,198KB → 219KB / −82%）。

## 1. EYESCREAM — 写真が UI そのもの

### 1-1. 1画面目が「写真の壁」（フルブリード・モザイク）
TOP の第1画面は **3×2 の写真6枚が隙間ゼロで画面を埋める**。ナビゲーションバーが無く、
ロゴ（左上）・SNSアイコン（右上）・PREV/NEXT（左右端の縦書き）だけが写真の上に浮いている。
記事タイトルは写真の上に直接置かれる（カテゴリ小 → タイトル太 → 日付）。

> **Techno Japan への示唆**: フェス一覧の1画面目を「今週のフェス6枚のモザイク」にする。
> 現状は見出し＋フィルタ＋文字リストで、1画面目に写真が0〜1枚しか無い。

### 1-2. カードが2種類あり、混在させている
- **A: 写真の上に文字を載せる**（特集・大きい枠）— 画像がカードそのもの。枠線も背景も無い
- **B: 写真の下に白いブロック**（通常）— カテゴリ（小・グレー）→ タイトル（太・2行）→ 日付（右下）

同じ一覧に A と B を混ぜることで、平坦なグリッドにリズムが出ている。

### 1-3. 1枠に複数写真を詰める「モザイクカード」
SNAP記事のカードは、**1枠の中に小さい写真6枚を 3×2 で敷き詰めている**。
「これは写真集だ」と開く前に伝わる。

> **Techno Japan への示唆**: フェスのフォトレポート記事、ラインナップ（アーティストの顔写真6枚）、
> 会場一覧のカードにそのまま使える。素材は既にある。

### 1-4. 記事は「写真1枚＝2画面」
特集記事（`culture/165133`）の実測:

| | 値 |
|---|---|
| 記事の高さ | **33,515px（37画面分）** |
| 写真 | 38枚 |
| 写真1枚の高さ | **1,754px**（viewport 900px の約2倍）／ 1,053px |
| 写真の幅 | 83% と 50% を**交互に** |
| 本文の幅 | 50%（h1・リード）／ 48%（キャプション） |
| キャプションの文字 | **12px**（本文16pxより小さい） |

写真を「読み飛ばせない大きさ」で置き、文字はキャプションとして**従属させている**。
記事の末尾では RECOMMEND（3カラム）の後に**次の記事がそのまま続けて表示される**（無限読み）。

## 2. Spincoaster — 密度と軽さの両立

### 2-1. 46枚で 539KB
srcset を 44/46 に付け、表示サイズに合ったファイルを選ばせている。
Techno Japan は **srcset が0**（カード画像が CSS の `background-image` なので付けられない）。

**実測した具体的な損**（Techno Japan TOP・モバイル dpr3）:

| 要素 | 表示サイズ | 必要な画素 | 実際に送っている画像 |
|---|---|---|---|
| `.fest-row-bg` | 432×313 | **1,297px** | `*-lg.webp` = **960px**（不足・ぼやける） |
| `.fest-row-thumb` | 345×110 | 1,035px | **同じ 960px ファイル**（同じ 100〜126KB を使い回し） |

`-sm` は 480px・31KB、`-lg` は 960px・126KB。**同じファイルを大小2か所に使っている**ため、
大きい場所では足りず、小さい場所では重い。`image-set()` か `<img srcset>` への移行で両方直る。

### 2-2. メタ情報の置き方
カード内は **カテゴリ（左）＋日付（右）を1行**にして、画像とタイトルの間に横罫のように置く。
文字は 14〜16px と大きく、遠目にも読める。抜粋文も著者名も無い。

> **Techno Japan との差**: TOP の文字は 9px×53箇所・8px×45箇所・10px×42箇所。
> **8〜10px が全体の多数派**。先日のコントラスト改善で濃さは上げたが、**サイズは小さいまま**。

### 2-3. 見出しの二段構え
ローマ字の固有名詞を **Oswald（condensed）50px** で大きく、日本語の説明を **15px** で下に置く。
Techno Japan も Bebas Neue（同系の condensed）を持っているので、同じ構造をすぐ作れる。

### 2-4. 記事の組み方
- ヒーロー: **幅100%・2.91:1・高さ495px** の横長バナー（EYESCREAM の縦長全画面とは正反対）
- 本文: **14px・幅37%（約530px）**の1カラム。本文中の写真も同じ530px幅に揃える（全幅にしない）
- 右レール（幅18%）に関連記事＋自社バーの告知を常時表示
- **クレジット行**を明示（`Interview & Text by 〇〇 / Photo by 〇〇`）
- Spotify / YouTube の埋め込みを本文幅で挿入

### 2-5. 背景に微細なノイズ
真っ黒ではなく、グレイン（粒子）テクスチャが乗っている。Techno Japan の `#080808` ベタ塗りより
「紙っぽさ」「実在感」が出る。CSS の 1枚の小さな PNG か SVG フィルタで実装できる。

## 3. Techno Japan に取り込むべき順（効果 × 手間）

### ★ A. フェス一覧・TOP の「写真密度」を上げる（最優先）
**現状**: フェス一覧はモバイル 6画面分で写真2枚。143枚の写真が使われていない。
**案**: 一覧の第1ブロックを「今月／直近のフェス 6枚のモザイク」（EYESCREAM 1-1）にし、
以下のリストも **写真つきカード**にする。1画面あたり 0.3 → **2〜3枚**を目標。
**前提**: B の実寸選択（導入済み）があるので、32枚を足しても sm/md 中心で約 +1.0〜1.9MB。
合計 2MB 前後で、Spincoaster の 15MB・EYESCREAM の 34MB に対してなお 1/7 以下に収まる。

### ★ B. カード画像を `<img srcset>` か `image-set()` に移す
**現状**: CSS background のため出し分けができず、960px の同じファイルを大小両方に使用。
**効果**: サムネは 31KB（-sm）で足り、大きいブロックには 1,440px 級の新しい派生を追加すれば
**ぼやけも解消**。写真を増やしても重くならない土台になる。
**注意**: 遅延読み込みの仕組み（`tjLazyBgAttr` / `tjApplyLazyBackgrounds`）と
`check_hub_pages.py` の `data-bg` 対応が連動しているので、置き換えは一括で行う。

### ★ C. 一覧の文字サイズを 8〜10px → 12〜14px に
**現状**: 8〜10px が多数派。Spincoaster は 14〜16px、EYESCREAM は 12〜16px。
**効果**: 先日のコントラスト改善（opacity 0.62）と合わせて、初めて「読める一覧」になる。
**注意**: サイズを上げるとカードの高さが変わる。1画面あたりのカード数が減るので、
写真密度（A）とセットで設計する。

### D. フェスレポート記事のフォーマットを作る
EYESCREAM 1-4 の型（写真 83%/50% 交互・キャプション 12px・写真1枚が1画面級）を
記事テンプレートに用意する。GA4 で**記事は46〜70秒読まれている**（フェス詳細は20〜35秒）ので、
写真主体の長い記事は Techno Japan の読者に合っている。

### E. カードに「複数写真モザイク」を導入
ラインナップ（出演者の顔6枚）、フェスのフォトレポート、会場の内観など。
1枠で「中身が写真集である」ことを伝える（EYESCREAM 1-3）。

### F. クレジット行と埋め込み
`Photo by` / `Text by` を記事下に明示（Spincoaster 2-4）。
フェス詳細に Spotify / SoundCloud のプレイリスト埋め込み（アーティストの音を聴ける導線）。

### G. 背景にグレインを乗せる（低コスト・見た目の質感）
`#080808` のベタ塗りに微細なノイズを重ねる。1枚の小さな画像か SVG フィルタで済む。

## 4. 真似しない方が良いもの

- **EYESCREAM の 33MB と Spincoaster の 15MB**: 画像 1 枚あたり 542KB / 292KB。
  Techno Japan は 57KB で、**配信は3サイトで最も良い**。密度だけ学び、配信は真似しない。
  （初版は「配信は Spincoaster に倣う」と書いていたが、計測の誤りに基づく結論だった。訂正済み。）
- **EYESCREAM のナビゲーション不在**: 1画面目にメニューが無い作りは、指名検索（フェス名＋年）で
  来る Techno Japan の読者には向かない。写真の下に「日程・会場・チケット」を出す現在の方針を維持する。
- **Spincoaster の右レール**: PC専用の作りで、Techno Japan の読者は**モバイル 455 / PC 166**（GSC実測）。
  モバイル優先の現状で右レールを足す意味は薄い。
